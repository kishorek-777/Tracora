# /p11 — Mobile PWA

10 dev-days — the largest phase, and the one an agent compresses least,
because most of the time is a phone in a hand. Depends on P4, P5, P8.

Read the PWA section of `.agents/rules/ui-conventions.md` in full. This
is the one screen with real design freedom; the rest of Tracora is a
Frappe desk and should look like one.

## Read

`docs/LLD.md` PWA section, `api.lookup.find_asset` spec, FR-30 to
FR-35, FR-91.

## Build — backend

**`api/lookup.py` — `find_asset(q)`**, whitelisted:
- Exact `asset_tag` → open that asset.
- Exact `serial_no` → open that asset.
- Partial `asset_name` → return up to twenty rows for the user to
  choose. **Never guess between multiple matches** (FR-91) — this came
  out of the edge-case review; do not regress it.
- No match → clear not-found response naming what was searched. Creates
  nothing.
- Payload: full asset with both companies, holder (name, code, mobile,
  email; branch/department when Internal, company/designation when
  External), open maintenance, active seats, last twenty movements.
- **Explicit field list, never `SELECT *`.** Never returns
  `aadhaar_number` or `permanent_address`.
- **Calls `doc.check_permission("read")` on the asset and the holder
  before returning anything.** `frappe.get_doc()` does not check
  permissions on its own (see `.agents/rules/frappe-framework.md`) —
  this endpoint fetches documents and hands data to a client, which is
  exactly the case that check exists for. This is a genuine gap, not a
  formality: without it, `find_asset` is a whitelisted read with no
  permission boundary at all.

## Build — UI, and this is the phase's real work

**Design pass before code.** Produce a short design plan first —
palette (state colours only, per the rules file), type scale, layout
sketch for each of the five screens — and put it in the implementation
plan for approval before building.

Five screens, all of which must be designed rather than defaulted:

1. **Scan** — one input, focused on load. Camera view with a clear
   framing guide. A visible "type instead" affordance, because damaged
   labels are the normal case, not the exception.
2. **Result** — the answer fills the viewport. What it is, who has it,
   where. Everything else below the fold. Status as a coloured chip
   with its text label, never colour alone.
3. **Multiple matches** — a list of up to twenty, each row showing tag,
   name, holder, location. Enough to choose correctly without opening
   each.
4. **Not found** — names what was searched, offers to search again.
   Creates nothing, offers no "add asset" path. Unknown assets are
   registered at a desk.
5. **No connection** — honest and immediate. Not a spinner that never
   resolves. This is a designed state, not an error toast.

Plus: camera permission denied must route to the typed fallback
obviously, not dead-end.

**Constraints from the rules file that are not negotiable**: 44px touch
targets, high contrast, large type, no offline data caching, service
worker caches the shell only.

**Install**: manifest with name, icons, `display: standalone`, start URL
`/scan`.

## Verification — evidence required

Browser subagent covers the layout and search paths. **It cannot test
the camera.** Split the evidence accordingly:

*Browser agent can demonstrate:*
- FR-91 — a name matching three assets returns three rows, not a guess.
- FR-34 — a no-match search naming what was searched; database row
  count unchanged.
- FR-35 — logged out, search unreachable.
- FR-32/33 — one screen showing asset and holder together.
- The network response inspected directly, showing no `aadhaar_number`
  or `permanent_address`.
- All five screens screenshotted at 375px width.
- 200% zoom still usable.

*Only a real phone can demonstrate — report which devices were used:*
- FR-30 — installed to a home screen, opens standalone.
- FR-31 — scanning a printed label from P7 resolves the same asset as
  typing its tag.
- Camera permission denial routing to the typed fallback.
- **Minimum two different physical phones.** Camera behaviour and
  permission prompts differ across devices and browsers, and that
  variance is what this phase's budget is actually for.

State plainly in the walkthrough which checks were browser-agent and
which were on hardware. Do not present a desktop Chrome screenshot as
evidence that scanning works.
