# /p12 — Permissions and PII verification

3 dev-days. Depends on P2–P9. This phase answers the build's last
genuine unknown.

## Read

`docs/LLD.md` permissions table and the `report_hide` note including
its "unresolved, must be tested" flag. FR-19, FR-39, NFR-02, NFR-03.

## Build

- **Role permissions on all thirteen doctypes.** Super Admin: full,
  including delete. Admin: read, write, create; delete on nothing.
- **Movement and Reminder Log**: neither role gets write or delete at
  the permission level — in addition to the code guards from P5 and P9,
  not instead of them. Permissions can be edited through the UI; code
  cannot. Both layers.
- **`track_changes: 1`** on every doctype, with a visible change log.

## The test that decides whether FR-39 actually holds

The LLD's claim that `report_hide` protects `aadhaar_number` and
`permanent_address` is **unverified**. Test all three routes on this
bench's actual Frappe version:

1. The Report Builder column picker.
2. A list view's export to Excel.
3. A raw `frappe.client.get_list` API call requesting those fields
   explicitly.

Report the actual result of each — pass, fail or partial. Do not assume
the LLD is right.

**If any route leaks**, implement the fallback: `permlevel: 1` on both
fields with form-level read granted and report permission left at
permlevel 0, which the report engine respects. Then re-run all three
tests.

## Build — UI

- **Verify what each role actually sees**, with screenshots from a real
  Admin session — not from Administrator with a role switched on. The
  delete button must be *absent*, not present-and-failing. A button
  that errors when pressed is a worse experience than no button, and it
  suggests the permission is a suggestion.
- Confirm the conditional action buttons from P5 respect role as well
  as status.
- Change-log visible and readable on at least one record of each major
  doctype.

## Verification — evidence required

- Screenshots from a logged-in Admin session showing delete absent on
  asset, employee, movement, licence.
- Console evidence: as **Administrator**, editing a movement via the
  API — still refused by the code guard.
- **Confirm every whitelisted method that reads a document and returns
  data — `find_asset` (P11), the HRMS subscribers (P3), any report
  helper — calls `check_permission` rather than relying on the
  `@frappe.whitelist()` decorator alone.** Grep for `frappe.get_doc(`
  across `api/` and `integrations/` and check each call site. This is
  a real gap `frappe.get_doc` leaves open by default, not a formality.
- **The three `report_hide` test results, each stated explicitly**,
  with the evidence for each. This is the most consequential unknown
  left in the build and this is where it stops being an assumption.
- If a fallback was needed, evidence that it closes the specific leak
  found.
