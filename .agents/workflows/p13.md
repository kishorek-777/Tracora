# /p13 — Data migration

5 dev-days. Depends on every prior phase.

## Two decisions this phase cannot start without

Confirm with Kishore before writing import scripts. If either is
unanswered, **stop and report** rather than guessing:

1. **Is the existing estate relabelled to the `TRC-` series, or are old
   labels kept as `Manual entry` tags?** This decides whether step 4 is
   "tag mode per asset from a source list" or "issue new labels for
   everything" — and the second is weeks of physical work.
2. **What date starts history for assets already in service?** The
   design default is the migration date, not an invented earlier one.
   Backdating produces a history that looks complete and is fabricated.

## Read

`docs/LLD.md` migration section, and the PRD design decision on
migration-dated movements.

## Build

Import scripts, in this order — each depends on the one before:

1. Companies, branches, departments — via P3's `bulk_import()` if HRMS
   has them, else CSV.
2. Employees. Code is the key; a duplicate **fails that row loudly**
   and does not silently merge.
3. Locations with coordinates — before assets, since location is
   mandatory.
4. Assets, tag mode per record per decision 1.
5. **Reset the tag series counter** to the highest imported `TRC-`
   number plus one, immediately after asset import. Without this the
   next auto tag collides with one just imported. Also make tag issue
   check the generated number does not already exist — belt and braces,
   because the counter lives outside the app's own data.
6. Current assignments as `Assign` movements dated per decision 2,
   **through P5's `assign_asset` endpoint** — not raw inserts, so the
   movement and the field write stay in one transaction like every
   other assignment in the system's life.
7. Licences and seats, after assets.

## Build — UI

- **Dry run first, always.** The import UI shows a summary before
  anything is written: counts per record type, and every row that would
  fail, with its reason. A silent import that half-worked is the worst
  outcome available here.
- **Results are a table, not a log dump.** Created / skipped / failed,
  with failures listing the source row and the reason in plain words —
  "Employee code AC-1204 already exists" not a stack trace.
- **Progress is visible** for long imports. A frozen screen during a
  four-thousand-row asset import will get killed by whoever is watching
  it.
- The Run for real button appears only after a dry run has been viewed,
  and states plainly what it will write.

## Verification — evidence required

- The full sequence run against a realistic sample on `mysite.local`.
- A duplicate employee code in the source stops that row with a clear
  message — screenshot the results table.
- After import, a new asset in `Auto-generated` mode gets a tag higher
  than every imported tag. Show the numbers.
- Every imported assignment has a corresponding `Assign` movement — not
  just a field value. Show the count matching.
- A licence imported with a past-due expiry gets FR-89's overdue
  treatment on the next reminder run, not silence.
- Confirmation that both decisions above were answered before any
  import code was written.
